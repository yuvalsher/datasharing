Data Sharing

Get analysis-ready data into a statistician’s hands.

A practical field guide for collaborators, students, and postdocs who need faster turnaround without hiding the raw story of the data.

Start the checklist

On iPhone or iPad: tap Share, then Add to Home Screen.

Who this is for

Scientific collaborators, consulting students, and anyone whose job is to collate or clean data before analysis begins.

  • Collaborators who need a statistician to analyze data
  • Students or postdocs looking for consulting advice
  • Junior statistics students preparing shared data sets

The Leek group’s experience is that the number-one source of delay is the state of the data on arrival. Statisticians should be able to handle data in whatever form it arrives — and still see the raw measurements, the processing pipeline, and hidden sources of variability. When processing steps are already standardized, doing that work first can dramatically speed turnaround.

What you should deliver

For maximum speed, hand over this four-part package.

  1. 01

    The raw data

    The rawest form you can access — untouched by summarization.

  2. 02

    A tidy data set

    Structured so each variable is a column and each observation is a row (Wickham’s tidy data).

  3. 03

    A code book

    Every variable, unit, summary choice, and study-design detail explained.

  4. 04

    An exact recipe

    The explicit steps from raw data to the tidy tables and code book.

The raw data

Include the rawest form of the data you have access to.

  • The strange binary file your measurement machine spits out
  • The unformatted Excel file with 10 worksheets from a contractor
  • The complicated JSON you scraped from an API
  • The hand-entered numbers you collected looking through a microscope

You know the raw data is in the right format if you:

  1. Ran no software on the data
  2. Did not manipulate any of the numbers
  3. Did not remove any data from the data set
  4. Did not summarize the data in any way

Reporting manipulated data as raw data is a common way to slow analysis — the analyst often has to forensically reconstruct why the numbers look weird.

The tidy data set

Follow the four principles of tidy data.

  1. Each variable you measure should be in one column
  2. Each different observation of that variable should be in a different row
  3. There should be one table for each “kind” of variable
  4. Multiple tables should include a linking column

Put full, readable column names in the first row — for example AgeAtDiagnosis instead of ADx. In Excel, use one file per table: no multiple worksheets, no macros, no highlighted cells. Or share CSV / tab-delimited text.

Genomics example: for 20 people with RNA-seq and clinical data, keep one spreadsheet for demographics (patient id, age, treatment, diagnosis) and another for summarized genomic counts linked by patient id.

The code book

Measurements need more detail than a spreadsheet header can carry.

At minimum, document:

  1. Variables and units not obvious from the tidy table
  2. Summary choices you made
  3. The experimental study design you used

A Word file works well: a “Study design” section describing collection, and a “Code book” section describing each variable and its units. Explain selection — first 20 clinic walk-ins, age-selected patients, randomized treatments, and so on.

How to code variables

Code by statistical data type — and prefer text over opaque numbers.

Continuous
Quantitative scales that can be fractional (weight in kg).
Ordinal
Few ordered levels (poor, fair, good) — store the words, not 1/2/3.
Categorical
Unordered categories (male/female) — store labels as text.
Missing
Unknown mechanism — code as NA. Do not impute or drop quietly.
Censored
Known missingness (below detection, lost to follow-up) — use NA and add a VariableNameCensored TRUE/FALSE column; explain why in the code book.

Encode every piece of information as exportable text. Color formatting and cell highlights will be lost when the sheet becomes raw text.

The instruction list / script

Reproducibility means others can go from raw data to your tidy output.

Ideally, write a computer script in R, Python, or another language that takes the raw data as input and produces the tidy data. Run it more than once and confirm identical output.

If you do not code, provide pseudocode — for example: run summarize software version 3.1.2 with parameters a=1, b=2, c=3 for each sample; take column three of each output file as the corresponding tidy row. Note the OS you used, and ideally have a labmate confirm they can reproduce the same file.

What you should expect from the analyst

A tidy package speeds the statistician — and still invites careful checking.

Expect:

  1. An analysis script that performs each analysis (not just instructions)
  2. The exact computer code used to run the analysis
  3. All output files and figures generated

Both the statistician and the scientist should understand the analysis. You may not rerun every step alone, but you should be able to explain why each step was done.
